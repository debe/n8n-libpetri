# Divergences from n8n

This register lists every n8n behaviour the engine does not reproduce, with its classification.
Nothing is skipped silently.

**Status** is `designed` once the row's mechanism has been observed — by n8n's own suite
(`docs/conformance-m2.md`, `docs/conformance-m3.md`, `docs/conformance-final.md`), by the
differential harness (`docs/differential.md`) or by a test that fails without the behaviour —
and `proposed` while it is still only reasoned from the code. Row 18 is the only one left at
`proposed`: the flags it names are written inside n8n's credential layer, which `FakeHost`
does not mirror, so no harness here can measure the violation.

A row can also be `fixed (M4)`: the behaviour was a real divergence, it was measured, and
then the model changed so the divergence is gone. Such a row stays in the register with its
mechanism intact — it is the record of what was wrong and of what the fix has to keep true,
and the differ still carries its attribution so a regression is named rather than reported
as an unattributed ordering difference. Row 20 is the only one.

| # | n8n behaviour | Classification | Rationale | Status |
|---|---|---|---|---|
| 1 | R6 stuck-join partial fire, starved-branch case | abandoned (cause removed) | Empty outputs are propagated as explicit tokens, so an AND-join always completes. This also covers the case where n8n does not partial-fire at all: R6 runs at the end of a loop iteration that ran a node, so an entry dropped at `isNodeFilteredOut` (line 74–76 `continue`) skips it, and if that entry was the last one the loop exits with the join still in `waitingExecution` and the node never runs. Observed by the differ on `diamond` with a `runNodeFilter` that excludes one branch: n8n runs Trigger, IF, A and stops; the net's empty token completes `Merge`, which then runs, and so does `End` | designed |
| 2 | R6 stuck-join partial fire, arrival-count mismatch | abandoned (defect surfaced) | A stranded token is a modelling error; the verifier flags it statically and the runtime reports it instead of silently re-running the join. **The static detector works since M5**: proper completion comes back `violated` on `ifBothOutputs` in ~15 ms off the state-class graph, naming `id:Merge/ready_0` and `id:Merge/hasdata` with the firing sequence that reaches the stuck marking (M4 measured the same question `unknown` at 600 s). Includes the resume corner: R6's `null` → `[]` substitution is a one-off per execution, so a join handed both a complete stack entry and a further arrival on another input strands instead of being padded a second time (that shape needs a producer to run twice, which is n8n-inconsistent for an acyclic workflow); the stranded encoder names the node and the place | designed |
| 3 | v0 execution order (R5 ancestor forcing) | out of scope | Queries live scheduler state; v0 workflows route to the legacy scheduler | designed |
| 4 | Slot-overwrite data loss in `addNodeToBeExecuted` | abandoned (defect) | Reproducing it would destroy user data | designed |
| 5 | Total-order `nodeExecutionOrder` assertions | replaced | LIFO artifact; replaced by data equivalence + happens-before. Two mechanisms produce the artifact and both keep node data equal: n8n's own stack discipline at k = 1 (row #12) and, above it, the concurrency the budget buys (row #21) | designed |
| 6 | Endless-loop guard (`currentExecutionTry === lastExecutionTry`) | abandoned | Cycles carry bounded iteration tokens; the verifier proves bounds | designed |
| 7 | Cross-branch `$('Y')` reference fails or succeeds by canvas order | replaced | The net waits for `Y` when it is reachable on another branch; an unmet reference (Y skipped or unreachable) fails with n8n's own error | designed |
| 8 | OR-input rounds that interleave (one producer delivers twice before its sibling once) | positional | Counted positionally like n8n's slots. `placeBound(X/ready_i, n)` is the query that proves a workflow free of it. **M4 measured that it did not close** on a compiled net (`unknown` at 30 s on the smallest OR shape there is); **M5 decides it** off the state-class graph instead — `proven` on `multiProducer` in a complete exploration (245 classes when this was written; 218 since M6), milliseconds, no solver (`docs/verification.md`, "The arrival bound"). So this row now has a working detector wherever the graph closes, and the limit is the graph's shape ceiling rather than the property. The join-slot form of the same query (capacity 1) closes too, but it cannot fail: every arm consumes `free_i` and only `X_start` / `X_skip` refund it, so that verdict is about the gadget, not about this row | designed |
| 9 | Non-all-required node wired only on a higher input (R6 runs it at quiescence with the lower input `[]`) | replaced | Compiled in direct form and run on arrival with the same data; only the timing differs | designed |
| 10 | OR-input node also fed by a cycle-edge producer: an all-empty round after cycle-triggered runs | positional | Cycle runs leave `ran_i` markers the round does not clear, so the node is not skipped; the downstream join then strands, which the verifier reports | designed |
| 11 | Several arrivals on one input: n8n runs the most recently produced arrival first | positional | n8n `unshift`s onto a stack it `shift`s from (`enqueueFn` in `addNodeToBeExecuted`, `popExecutionStack`), so the last arrival runs first; the net's OR round delivers in arrival order, `X/hasdata_i` being FIFO. It is *arrivals*, not producers: one producer that ran several times backs the same LIFO up, as `userCycle`'s `Exit` does (`B` produced three times, two `Exit` activations queued, n8n took the most recent first). Everything those activations passed moved with them. The node runs the same number of times with the same payloads, but their order — and therefore which `runIndex` holds which — is reversed. Observed on n8n `workflow-execute.test.ts` "v1 execution order > should run node twice when it has two input connections" (`Set2` fed by `Start` and by `Set1`). | designed |
| 12 | v1 enqueues a completed multi-input entry at the front of the stack, so a join runs after every sibling already queued | replaced | The mechanism behind #5's total-order artifact: `addNodeToBeExecuted` pushes an entry whose inputs are all present with `unshift`, and the loop `shift`s, so a join that became ready while siblings were queued runs last. The net fires it as soon as it is enabled, at priority = DAG depth. Node data is unchanged; only `executionIndex` differs. Observed on n8n `workflow-execute.test.ts` "v1 execution order > should run complicated multi node workflow where multiple Merge-Node have missing data and complex dependency structure": n8n runs `Start, Set1, IF1, IF2, IF3, IF4, Merge1, Merge2, Merge4, Merge5, Merge6, Merge7`, the net runs `Start, Set1, IF1, Merge1, IF2, Merge2, Merge4, IF3, IF4, Merge5, Merge6, Merge7` — `Merge1` becomes ready when `IF1` routes and the net fires it there, where n8n's `unshift` puts it behind `IF2`–`IF4`. **M4 correction**: M2 and M3 also attributed "… depth-first & the most top-left one first" to this row. That was wrong — it was row #20, the OR-input arm latency, and the case passes now that row #20 is fixed. This row has exactly one witness in n8n's suite. | designed |
| 13 | After a destination-node stop, n8n's loop keeps popping the stack and drops out-of-filter entries at `isNodeFilteredOut` | replaced | The net deposits `_pause` and quiesces, so an in-filter entry still pending at that moment never runs; **M4 widened the reach of this**: with row #20 fixed the net is depth-first again, so the destination node runs *earlier* and `_pause` lands before a sibling n8n would have popped afterwards. Measured on the `destinationStop` differ fixture (Trigger → A, B; A, B → C.0, destination `C`): n8n runs `Trigger, A, C, B, C`, the net now runs `Trigger, A, C` and `runData.B` is absent where before the fix `B` happened to run before the pause. Same rule, more of it — a data difference, and inside this row's abandonment, not a defect; out-of-filter entries are dropped as n8n drops them, but only the predicate is consulted — no `createTaskStartedData`, so no `executionIndex` is consumed. At k > 1 the pause additionally lets every sibling already in flight finish and be recorded (row #17): `_pause` inhibits only `X_start` / `X_start_unmet` / `X_retry_wait`, so a node that had already started completes and routes, and its successors' entries are what the codec writes back | designed |
| 14 | An entry whose `ensureInputData` is false is deferred and then raises n8n's endless-loop `UserError` | abandoned (see #6) | The activation is dropped with a diagnostic and routes all-empty so downstream joins still complete. Unreachable for entries the scheduler itself produces; only n8n-authored stack state can carry an entry without `data.main` | designed |
| 15 | `runExecutionData.waitTill` is execution-global: the loop `break`s on it immediately after the node that set it | positional (k > 1 only) | With one node in flight the field can only have been set by that node, so k = 1 is byte-identical. At k > 1 the claim is made in the same synchronous turn in which a node's own `runNode` resolves, so claim order is the order the runs finished: (a) a node that started after the field was already set never claims (`waitTill === before`); (b) of the nodes that saw it change during their own run, the first whose `runNode` resolved keeps it; (c) a refused claim is reported by diagnostic, the node is recorded normally, and the `executionStatus: 'waiting'` that `host.createTaskData` stamped on it — it reads the same global field — is corrected to the status the run actually had. What stays undecidable from outside the node: one that sets the field and then keeps working while a sibling finishes loses the claim to that sibling, and the execution then resumes the sibling instead of the Wait node. Closing it needs a write barrier on the field plus `AsyncLocalStorage` around `runNode` (ADR 0006) | designed |
| 16 | `runExecutionData.resultData.lastNodeExecuted` is the last node the loop ran | positional (k > 1 only, **plus** the k = 1 case below) | The field is written by every successful run (`stack-scheduler.ts:196`) and by `reportNodeExecutionError`. At k > 1 it is the last node to **complete**, which is the definition of the field under concurrency, not a corruption. At k = 1 the two engines run the same activations in the same order *as long as they run the same activations*: where another row makes the sets differ, the last completion differs with it and this field goes with it. **Observed in M4** on the `ifBothOutputs` differ fixture at k = 1: n8n runs `… Merge#0, End#0, C#1, Merge#1, End#1` and writes `End`; the net strands the second `Merge` arrival (row #2) so its last activation is `C#1` and it writes `C`. The differ attributes that row to #5 (total order abandoned) and it appeared only in M4, when the depth-first fix (row #20) moved `C#1` behind `End#0`. So: at k = 1 this field is stable **unless** a stranding or a stop row already made the activation sets differ. Consumers use it for the failed/last-run marker on resume, so a parallel branch finishing after the branch of interest moves the marker | designed |
| 17 | A sibling already running — or started inside the halt window — when the execution halts, pauses or stops would never have run at all under n8n | abandoned (EXEC-040) | n8n `break`s out of the loop, so a node it has not yet popped never runs. The net cannot un-start an action: `_halt` / `_pause` inhibit `X_start`, but every activation already in flight finishes, is recorded in `runData` and routes its output, and the successors it enqueues are written back onto `nodeExecutionStack` where n8n's `break` would have left them. **The window is wider than "already in flight"**: `_halt` reaches the marking only when the failing action *resolves*, and that resolution is behind n8n's own awaited error hooks (`handleNodeExecutionError` awaits `sendChunk`, `workflow-execute.ts:2050`, and `nodeExecuteAfter` on the stop path), so a sibling that completes inside it refunds a budget unit and a *new* `X_start` can fire — a node can therefore **start** after the failure is already known. That is the same window in which a sibling's completion could once overwrite the halting error (row #19). So at k > 1 a halted or paused execution can hold task data for nodes a k = 1 run would not have reached. Impossible at k = 1 (one node in flight, and it is the one that halted). **Observed in n8n's own suite at k ≥ 2**: `webhook-respond-branch-order.test.ts` "skips the Respond node when the work node runs first and fails" — a `responseMode: responseNode` webhook fans out to the work node (y = 500) and to a shared Respond node (y = 1000); n8n runs the work node, it throws, the loop `break`s and the Respond node never runs. At k ≥ 2 both children take a budget unit in the same scheduling cycle, so the Respond node is already in flight and the caller is answered where n8n would have left it unanswered. The difference is bounded to the *set of activations* and the pending stack entries that follow from it: the halting error is unchanged (row #19 keeps it write-once) and no run either budget performed carries a different payload, which `tests/conformance/budget-equivalence.test.ts` pins across k ∈ {1, 2, 4, 8}. This is the one k > 1 behaviour change a user can see; keep k = 1 for a workflow whose correctness depends on a failure suppressing a sibling | designed |
| 18 | `additionalData.currentNodeUsedDynamicCredentials` / `…Attempted…` are per-node, scoped by "one node runs at a time" | positional (k > 1 only) | They are reset per node (`resetDynamicCredentialsUsage`), written by n8n's credential layer **inside** `runNode`, and read back in `createTaskData`. Above k = 1 a sibling's reset can land between another node's credential resolution and its own read, so `ITaskData.usedDynamicCredentials` can be lost or attributed to the wrong node. Nothing outside `WorkflowExecute` can scope them: the write is not ours and the window spans an await we do not own. Recommendation: keep k = 1 for workflows that use dynamically-resolved credentials | proposed (M3) |
| 19 | `executionError` is one execution-global field the loop clears at the top of every iteration and every retry | positional (k > 1 only) | n8n's `this.executionError` (`stack-scheduler.ts:29`, cleared at lines 56 and 107) is safe because one node is in flight and the loop `break`s on the halting one; `processRunExecutionData` reads it after `run()` and persists the execution as a success or a failure by it (`workflow-execute.ts:2250-2255`). The scheduler keeps two values instead: the **halt error** is written once by the activation whose failure ended the execution and is never overwritten, and the **leftover** — what the field still held when an activation completed, i.e. an error its `onError` policy continued past — follows completion order. At k = 1 completion order is iteration order, so the value is byte-identical. Above k = 1 the leftover is the last activation to *complete*, not the last in n8n's total order, exactly as `lastNodeExecuted` is (row #16): a workflow whose only continued error is not the last completion reports no error where a differently-ordered run would have reported one | designed |
| 20 | An OR-input node's arm transition costs one scheduling cycle, so a shallower sibling takes the budget unit in it | **was** positional; now none | **Fixed in M4 by moving the `_budget` refund off `X_route` onto `X_done`.** *The mechanism*: the OR-input gadget turns an arrival into `X/ready_i` + `X/hasdata_i` on a separate `arm` transition, and libpetri's executor collects its ready set from the enablement flags **before** the firing pass — only `updateDirtyTransitions()` sets them (`precompiled-net-executor.ts` `fireReadyGeneral`) — so a transition another firing enables during that pass fires no earlier than the next cycle. `X_route` used to deposit the edge tokens *and* refund `_budget` in one firing, so the shallower budget-blocked sibling's `X_start` was evaluable one whole cycle before the armed deeper consumer's and took the unit. Observed on `multiProducer` (Trigger → A, B; A, B → C.0): n8n ran Trigger, A, C, B, C, the net ran Trigger, A, B, C, C at k = 1. *Why a priority band is not the fix*: measured, and it changes nothing — priority only orders the ready set that was already snapshotted, so raising the arm above every start still leaves the deeper `X_start` out of that pass. *The fix*: the refund moved off the firing that deposits the edge tokens and onto `X_done`, which consumes the `X/routed` that firing marks and refunds `_budget` one cycle later — the same cycle the `arm` fires in. (M4 achieved that by making every node with a connected output route per output, `SPLIT_ROUTING_ABOVE` = 0; **M6 supersedes that half**: `X_run` routes inside its own `Out` spec at or below three connected outputs, `X_done` is unconditional, and the phase is unchanged, so this row's fix stands — see ADR 0004's M6 amendment.) Both candidate `X_start`s then land in one ready set and priority = DAG depth decides, as the README says it does. *Measured after*: `multiProducer` is `order: equal` at k ∈ {1, 2, 4}, `ifBothOutputs` loses its ordering rows #11 and #12 entirely, and n8n's own `v1 execution order > should execute nodes in the correct order, depth-first & the most top-left one first` passes at k = 1 (it failed in M2 and M3, where it was attributed to row #12 — wrongly: that case was this row, not the unshift). The row stays in the register because the differ still names the mechanism, so a phase regression is reported as row #20 and not as an unattributed ordering difference | fixed (M4) |
| 21 | n8n runs one node at a time, so a workflow's total execution order is a property of the graph plus canvas position alone | replaced (k > 1 only) | The reason the project exists (README "Why"). Above k = 1 every node whose inputs are ready takes a budget unit, so two branches with no dependency either way run at once and `executionIndex` records the order they *started* — the order the budget allocated — rather than n8n's depth-first walk. Node data is untouched, and structurally so: the compiler's k-safety check leaves a budget above 1 only on an acyclic workflow with at most one producer per input index, where every node fires exactly once and its input on index *i* is its unique producer's output, so `runData` is determined by the graph and not by the schedule. Observed on n8n `workflow-execute.test.ts` "v1 execution order > should run complicated multi node workflow": n8n runs `Start, Set1, Set3, Set4, Set2, Merge1, Merge2, Merge3, Merge4`, the net at k ≥ 2 runs `Start, Set1, Set2, Set3, Merge1, Set4, Merge2, Merge3, Merge4`, because `Set2` and the `Set3 → Set4` chain have no dependency either way. Every node still runs once with the same payload — measured by the `complicatedMulti` differ fixture, which reports `data: equal` at every budget and attributes all four moves to the concurrency itself. A second witness arrived in M4: `v1 execution order > should execute nodes in the correct order, depth-first & the most top-left one first` passes at k = 1 since row #20 was fixed and fails again at k ∈ {2, 4} — 23 nodes whose independent branches the budget lets go at once. Row #5 records that the assertions are replaced; row #12 records n8n's LIFO mechanism at k = 1; this row records the mechanism the budget introduces | designed |
